## Preparing Your Thermodynamics Knowledge Base

### Splitting Large Documents Strategically

Dify enforces a **15 MB maximum file size** and **20-file batch upload limit**. For an 800-page textbook, split the PDF into four parts (~200 pages each). Name files sequentially (`thermodynamics_part1.pdf` through `thermodynamics_part4.pdf`) to maintain logical organization.

**Recommended KB composition for a Bachelor-level thermodynamics course:**

| Source category | Example files | Chunking note |
|-----------------|---------------|---------------|
| Core textbook (Thermo 1 + 2) | 800 pages split into 4 × ~200 pp | Parent-Child, paragraph delimiter |
| Old exam papers (*Altklausuren Thermo 1 + 2*, Bachelor level) | One PDF per semester | Regex delimiter: `\n\n(?=Aufgabe \d+\|Problem \d+)` keeps each problem and its solution in the same parent chunk |
| Lecture notes / professor handouts | Per chapter | Default Parent-Child |
| Recent research articles | 1 file each | Default Parent-Child |

`[screenshot: Knowledge Base creation dialog with Parent-Child Mode selected and Unstructured ETL highlighted]`

### Creating Your Knowledge Base

Navigate to **Knowledge** in the main navigation bar and click **Create Knowledge**. Name it descriptively: `Thermodynamics_Textbook_2025`.

For upload, select batch upload and add all four PDF parts simultaneously. **Select Unstructured ETL** as your processing solution — this is critical for academic PDFs. Unstructured ETL provides advanced parsing for complex layouts, tables, equations, and mathematical notation.

### Parent-Child Chunking: The Academic Document Advantage

Select **Parent-Child Mode** for your chunking strategy. This two-tier approach creates large parent chunks (paragraphs/sections) for comprehensive context, while generating small child chunks (sentences) for precise retrieval. When a query matches a child chunk, the system returns the entire parent chunk to the LLM.

**Recommended configuration:**

| Setting | Value | Reason |
|---------|-------|--------|
| Parent mode | Paragraph | Preserves complete concept explanations |
| Parent max length | 1,800 tokens | Captures full equation derivations |
| Child delimiter | `[.!?]\s+` | Sentence-level precision |
| Child max length | 300 tokens | Enables specific term matching |

Enable both text preprocessing options: **"Replace consecutive spaces, newlines, tabs"** and **"Remove URLs and email addresses"**.

### Indexing and Embedding Configuration

Select **High-Quality Mode** for indexing — this generates vector embeddings enabling semantic search, essential when students ask conceptual questions that don't match exact textbook terminology.

Choose **jina-embeddings-v2** as your embedding model. Its **8,192-token context length** dramatically outperforms standard 512-token models, ideal for extensive technical content.

### Retrieval Configuration: Hybrid Search with Reranking

Configure **Hybrid Search** combining semantic and keyword approaches:

* Semantic weight: **0.7**
* Keyword weight: **0.3**
* Rerank model: **Cohere Rerank** (production) or **Jina AI Reranker** (open-source)
* TopK: **6** chunks per query
* Score threshold: **0.5**

> If irrelevant results appear, increase threshold to 0.6–0.7. If important information seems missing, decrease to 0.4–0.45 and increase TopK to 8.

### Processing Time and Validation

Click **"Save & Process"** and expect **60–120 minutes** for an 800-page collection. Once complete, use the built-in **Retrieval Test** feature with sample queries:

* "What is the Carnot efficiency?"
* "Explain the relationship between enthalpy and internal energy"


```
Industry 4.0 applications. Your writing adheres to formal academic standards,
employs precise technical terminology, and maintains pedagogical clarity for
peer-reviewed publication audiences.

Generate a 3,000–5,000 word academic article structured as:
(1) Abstract (250 words)
(2) Introduction with literature review (800 words)
(3) Theoretical Framework covering thermodynamic principles (1,200 words)
(4) Industry 4.0 Applications with case studies (1,500 words)
(5) Critical Analysis (800 words)
(6) Conclusions and Future Directions (500 words)
Include in-text citations for all claims.
```

**Mandatory LaTeX rendering instruction** (append to every system prompt):

```
Render all equations in LaTeX inside Markdown:
- Inline math:   $\eta_{Carnot} = 1 - T_c/T_h$
- Display math:  $$\Delta S \geq \frac{\delta Q}{T}$$
Use SI units. Distinguish intensive (lowercase) from extensive (uppercase) properties.
```

Dify's frontend renders KaTeX in Markdown output, so equations display correctly in the final paper without additional post-processing.

### Incorporating Professor-Specific Guidelines

```

convention for work interactions. All temperatures must use Kelvin unless
explicitly comparing to other scales.
```

| Parameter | Value | Reason |
|-----------|-------|--------|

## Advanced Workflow Architecture: Deep Research Loops

### Understanding the Loop Node

Dify's Loop node enables knowledge accumulation across iterations — unlike simple list iteration, Loop nodes access outputs from both current and previous cycles, creating a knowledge network that mirrors the human research process.

### Three-Phase Deep Research Workflow

**Phase 1: Intent Identification**

Create a Start node with:
* `research_topic` (string): e.g., "Exergy analysis in combined heat and power systems for Industry 4.0"
* `max_iterations` (number): typically 10

Add an LLM node for Intent Analysis that clarifies the research goal and generates focused questions. Include an initial knowledge retrieval node for foundational background.

**Phase 2: Iterative Exploration (Loop Node)**

Configure the Loop node to track six variables:

| Variable | Type | Purpose |
|----------|------|---------|
| `findings` | array | New knowledge per cycle |
| `executed_queries` | array | Prevents redundant searches |
| `current_loop` | number | Iteration counter |
| `visited_urls` | array | Source tracking for citations |
| `knowledge_gaps` | array | Identified information needs |
| `image_urls` | array | Visual content references |

Inside the Loop:

1. **Reasoning LLM Node** (Temperature: 0.3) — evaluates `{loop.findings}`, reviews `{loop.executed_queries}`, generates 2–3 follow-up questions targeting unexplored aspects
2. **Research Agent Node** — uses knowledge base retrieval, web search (Exa Search), and content extraction autonomously; enable the "think" tool for meta-cognitive reflection
3. **URL Extraction Code Node** — parses agent responses and extracts source URLs via regex
4. **Variable Assigner Node** — appends new findings, updates executed queries, increments counter
5. **IF/ELSE Continuation** — continues if `current_loop < max_iterations` AND `knowledge_gaps is not empty`

**Phase 3: Synthesis**

After loop exit, a Final Summary LLM node (Temperature: 0.2, max tokens: 8,000+) receives the complete `{loop.findings}` array and synthesizes findings into a coherent academic article.

### Typical Execution Pattern for Thermodynamics

| Iteration | Action |
|-----------|--------|
| 1 | Retrieves basic exergy principles from textbook |
| 2 | Identifies CHP systems need more detail, queries specific chapters |
| 3 | Recognizes lack of Industry 4.0 apps, invokes web search |
| 4–6 | Gathers supporting technical data |
| 7–8 | Identifies contradictions, seeks clarification |
| 9–10 | Final validation and gap-filling |

## Multi-Agent Coordination *(Optional Advanced Pattern)*

> A single well-prompted workflow with the Deep Research loop is usually sufficient. This section describes a four-role specialization that helps when papers must withstand peer review.

### The Scout / Analyst / Critic / Architect Pattern

This pattern mirrors how a human research group works: a **Scout** surveys the territory, an **Analyst** extracts the numbers, a **Critic** challenges the draft, and an **Architect** assembles the final manuscript.

| Agent | Model | Temp | Responsibility |
|-------|-------|------|----------------|
| **Scout** | Claude Sonnet 4.6 | 0.4 | Surveys KB + web, surfaces candidate sources, identifies knowledge gaps |
| **Analyst** | GPT-4o | 0.2 | Extracts equations and numerical results, computes derived quantities, produces structured JSON |
| **Critic** | Claude Opus 4.8 | 0.1 | Adversarial review: factual accuracy, citation completeness, logical consistency, scores draft 0–10 |
| **Architect** | Claude Opus 4.8 | 0.2 | Composes the final draft, enforces section structure, handles cross-references and bibliography |

### Sequential Handoffs

Use **Variable Assigner nodes** after each agent to store outputs (`scout_findings`, `analyst_results`, `critic_report`). Each downstream agent receives all previous outputs as input context:

```
You are the Critic. Review the Architect's draft below against the Scout's
sources and the Analyst's extracted values. Flag any unsupported claims.

Draft: {architect_draft}
Sources: {scout_findings}
Numerical results: {analyst_results}
```

### Sequential vs Parallel

Use **sequential** when later agents depend on earlier outputs (Scout → Analyst → Architect → Critic). Use **parallel** branches only when sections are genuinely independent (e.g., introduction and methodology can draft in parallel before the Architect merges them via a Template node).

## Human-in-the-Loop Review *(Optional)*

For high-stakes publications — graded coursework, thesis chapters, conference submissions — insert a manual review checkpoint between the Architect and the final formatting node.

**When to use:**
* Professor approval required before final formatting
* Critic score is borderline (e.g., 7.5–8.5) and a human should arbitrate
* Sources disagree and the Architect surfaced a conflict that needs scholarly judgment

**Two implementation patterns in Dify:**

1. **Pause-and-resume via Conversation Variable**
   - The Architect writes the draft into a Conversation Variable
   - An **Answer node** displays the draft and prompts the user to either confirm (`/approve`) or annotate with edits
   - The next branch reads the variable and proceeds when an approval token is present

2. **External webhook checkpoint** *(self-host only)*
   - **HTTP Request node** posts the draft to a review tool (Notion, Linear, internal app)
   - Workflow halts until a `PATCH /resume` call returns with the reviewer's edits
   - Suitable for asynchronous overnight reviews

Pattern overview:

```
Architect → Answer (paused, displays draft) → [human edits] → Continue → Formatting → End
```

## Knowledge Pipeline for Complex Document Preprocessing

### When Standard Upload Isn't Sufficient

For thermodynamics materials including scanned exam solutions, handwritten problem sets, or mixed German–English content, **Knowledge Pipeline** provides advanced preprocessing. Access via **Dashboard → Knowledge → Create from Knowledge Pipeline**.

### Pipeline Architecture for Academic Documents

1. **Source Connection node** — uploads your document
2. **Parse Node** — select Unstructured parser for complex PDFs (handles tables, figures, equations, mixed layouts)
3. **Code Node** — custom preprocessing:
   - Remove headers/footers (page numbers, chapter titles)
   - Normalize equation formatting
   - Detect language switching between German and English sections
   - Mark problem numbers vs. solution text
4. **LLM Enrichment Node** (GPT-4-Vision) — for each chunk, extracts: main concepts, equations with purpose, whether content is theory/example/solution
5. **Parent-Child Chunk Node** — 1,800-token parents, 300-token children
   - Custom delimiter for problem sets: `\n\n(?=Problem \d+|Aufgabe \d+)`
6. **Embed Node** — jina-embeddings-v2
7. **Load Node** — High-Quality indexing, Hybrid Search, Rerank enabled

### Handling LaTeX Equations and German Language

Configure the Parse Node to maintain mathematical notation rather than converting to plain text. For mixed-language documents, jina-embeddings-v2 creates embeddings in a shared semantic space where "Enthalpie" and "enthalpy" map to similar vector locations. Tag chunks with a `language` metadata field (`"German"`, `"English"`, `"Mixed"`) for optional filtering.

## Complete Workflow Example: End-to-End Paper Generation

This 12-node production workflow generates publication-quality papers with iterative quality control.

### Input Configuration (Start Node)

| Variable | Type | Example |
|----------|------|---------|
| `research_topic` | string | "Exergy analysis for waste heat recovery in automotive manufacturing" |
| `target_word_count` | number | 4500 |
| `professor_guidelines` | string | Professor's specific requirements |
| `quality_threshold` | number | 8.5 (scale 0–10) |

### Workflow Nodes

**Node 2 — Topic Analysis LLM (Sonnet 4.6, temp: 0.3)**
Generates 5 research questions covering theoretical foundations, state-of-art, industrial applications, challenges, and future directions. Output: `research_questions`.

**Node 3 — Deep Research Loop (Scout agent, 8 iterations, `max_loops = 8`)**
* 3a: Knowledge Retrieval (TopK: 10, Rerank enabled) → `textbook_content`
* 3b: Scout Agent — Sonnet 4.6 with Exa Search, Exa Content, Wikipedia → `web_research`
* 3c: Synthesis LLM (Sonnet 4.6, temp: 0.25) → `iteration_summary`
* 3d: Variable Assigner — appends to `accumulated_findings`, extracts citations
* 3e: Gap Assessment LLM (**Opus 4.8**, structured JSON output) → updates `knowledge_gaps`
* 3f: IF/ELSE — continue if gaps remain AND `current_loop < max_loops`

**Node 4 — Analyst (GPT-4o, temp: 0.2)**
Extracts equations and numerical values from `accumulated_findings` into structured JSON (`{equation_id, latex, units, value, source}`). Output: `analyst_results`.

**Node 5 — Architect: Initial Draft (Opus 4.8, temp: 0.2, max tokens: 8,000)**
Uses `accumulated_findings`, `analyst_results`, `professor_guidelines`. Output: `draft_v1`.

**Node 6 — Critic: Quality Evaluation (Opus 4.8, temp: 0.1)**
Scores draft 0–10 against: technical accuracy, literature completeness, Industry 4.0 clarity, logical structure, critical analysis, citation quality, writing tone. Output: `quality_score`, `critique`.

**Node 7 — Quality Gate IF/ELSE**
* `quality_score >= 8.5` → optional HITL or directly to formatting (Node 11)
* Below threshold → refinement loop (Nodes 8–10, `max_loops = 3`)

**Nodes 8–10 — Refinement Loop**
* Parameter Extractor → `improvement_tasks`
* Architect rerun (Opus 4.8) — addresses specific weaknesses from `critique`
* Re-evaluation by Critic — if still below threshold and under 3 iterations, continues; otherwise proceeds

**Node 11 — Formatting Template (Jinja-2)**
Applies markdown headers, equation numbering, citation format `[1]`, bibliography generation.

**Node 12 — Citation Validator (Python Code node)**
Checks all citations have source entries, no orphans, correct ordering, flags issues. **No LLM cost.**

**Node 13 — End Node**
Outputs: `final_paper`, `quality_metrics`, `research_log`, `total_sources`.

### Abbreviated Workflow YAML

A trimmed view of the node graph and model assignments (illustrative — Dify's exported DSL is more verbose):

```yaml

  - id: start
    type: start
    outputs: [research_topic, target_word_count, quality_threshold]
  - id: topic_analysis

    type: llm
    model: gpt-4o
    temperature: 0.2
  - id: architect
    type: llm
    model: claude-opus-4-8
    temperature: 0.2
    max_tokens: 8000
  - id: critic
    type: llm
    model: claude-opus-4-8
    temperature: 0.1
  - id: refinement_loop
```

## Troubleshooting Common Issues

### Documents Becoming Inactive

Dify automatically disables documents not retrieved within **7 days (Sandbox)** or **30 days (Professional)**. Navigate to **Knowledge → Your Knowledge Base → Documents** and click **"Enable"** on inactive documents. To prevent this, schedule a monthly retrieval test resetting the inactivity timer.

### Slow Retrieval or Timeout Errors

| Cause | Solution |
|-------|----------|
| TopK > 10 with reranking | Reduce TopK to 6–8 |
| Multiple knowledge bases without metadata filtering | Add conditional routing by topic keywords |
| 4,000-token General Mode chunks | Switch to Parent-Child Mode |
| API rate limits exceeded | Use Professional Plan (100 req/min) |

Implement caching for frequent thermodynamics questions via **Annotation Reply** — the system serves common Q&A instantly without LLM calls.

### Poor Retrieval Accuracy for Technical Terminology

* **Lower threshold temporarily** to 0.3–0.4 to inspect near-miss chunks
* **Enable Hybrid Search** if using pure vector search — technical terms benefit from exact keyword matching
* **Verify embedding model** handles German scientific terminology (use jina-embeddings-v2 or multilingual-e5-large for mixed-language content)
* **Increase parent chunk size** to 2,000 tokens if equations split across boundaries
* **Add domain metadata** (`topic: ["heat_transfer", "thermodynamic_cycles", "exergy"]`) for pre-filtering

### Variable Size Limit Errors (Cloud Version)

When accumulating findings across loop iterations exceeds Cloud variable limits:

* Serialize and compress data in Code nodes before storage
* Store large content in external databases, keeping only IDs in Dify variables
* Break large workflows into smaller sub-workflows
* Migrate to self-hosted Community Edition for more generous limits

### LaTeX Equations Displaying Incorrectly

* Enable Markdown rendering in retrieval display settings — Dify renders KaTeX
* Verify the system prompt instructs the model to emit `$...$` (inline) and `$$...$$` (display) math
* Use LLM Enrichment Node to describe equations in plain language stored as metadata
* Include links to original PDF page numbers in citations
* Explicitly state "See source document Equation X for mathematical formulation" when precision matters

### Workflow Runtime Ceiling (~1 Hour)

Dify Cloud caps a single workflow execution at roughly **one hour**. Deep Research loops with high `max_loops` plus a refinement loop can hit this ceiling.

**Workarounds:**

* **Cap `max_loops`** at 6–8 for Deep Research and 3 for Refinement (`max_loops` is enforced inside each Loop node and is your primary safety valve)
* **Flow-splitting**: extract the Deep Research loop into a *sub-workflow* exposed via an internal HTTP endpoint. The parent workflow calls it asynchronously and persists results in Conversation Variables, then resumes with drafting in a second execution
* **Batched / scheduled runs**: trigger long jobs overnight via webhook so a timeout simply restarts at the next pending step
* **Self-host workaround**: increase Celery worker timeout in `.env`:
  ```bash
  CELERY_BACKEND_TIMEOUT=7200      # 2 hours
  WORKFLOW_MAX_EXECUTION_TIME=7200
  ```

NotebookLM accelerates the *what should I read?* phase; Dify automates the *how do I turn it into a paper?* phase.

For 800-page collections and sophisticated workflows, self-hosting provides:
* Unlimited variable sizes (eliminates Cloud workflow constraints)
* Complete data sovereignty (GDPR compliance)

```bash
git clone https://github.com/langgenius/dify.git

cp .env.example .env

```

Configure PostgreSQL for metadata, Redis for caching, and your choice of vector database (Weaviate default, Qdrant or Milvus for advanced needs).

**Performance optimizations:**
* Set `DB_POOL_SIZE=20` for PostgreSQL connection pooling
* Enable Redis caching to reduce repeated knowledge base query load

## Conclusion

Dify Professional Plan, accessed freely through student verification, transforms academic publication generation from a weeks-long manual process into a systematic, reproducible workflow completing in hours.

* **Invest 2–3 hours** upfront optimizing chunking strategy and system prompts
